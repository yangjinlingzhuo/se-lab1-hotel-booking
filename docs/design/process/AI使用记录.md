# 实验二 AI 辅助使用记录

本文件记录实验二中使用大模型辅助设计 UML 图的过程，包括使用场景、生成结果、人工审查、修改结果及优缺点分析。最终设计均由本人依据实验一需求核对确认。

## 记录 01：软件架构包图（2026-11-05）

- **使用场景**：依据实验一需求（REQ-001 ~ REQ-025）设计软件整体架构，用 PlantUML 绘制包图，表达模块划分与模块间依赖。
- **输入材料**：实验一最终需求列表（25 条）、实验一报告 PDF（图风格参考）、符子建同学的 AI 初稿与修改稿（对比参考）。
- **工具与环境**：使用 Kimi 辅助生成和修改 `.puml` 源码，采用本地 PlantUML 1.2026.9 渲染为 PNG。

### 生成与迭代过程

1. 初稿采用表现层、应用层、领域层和基础设施层四层结构，并将应用层划分为八个业务模块。初次渲染出现英文别名外露、层级错位和依赖线交叉等问题。
2. 调整为横向布局后，标签遮挡和交叉进一步增加，因此恢复纵向分层。
3. 加入隐藏布局约束时，其与“订单履约—领域规则—定时任务—订单履约”依赖形成环，导致 Graphviz 渲染超时。
4. 根据本人反馈，删除定时任务的反向箭头，改用说明文字表达触发关系；跨层的日志和持久化访问也改为注释，保留关键依赖。
5. 终稿采用与实验一一致的浅青绿色调，并重新排列模块，使四层结构和依赖方向更清晰。

### 人工审查与设计结论

- 表现层仅访问应用层，不直接修改库存或持久化数据。
- 订单状态机、库存一致性和报价计算集中在领域规则中，应用层负责业务流程编排。
- 定时任务属于基础设施，但会触发应用服务。图中用注释表达该关系，避免反向依赖影响结构阅读。

### 优缺点分析

- **优点**：能够快速将需求归纳为分层结构和业务模块，并辅助分析 PlantUML 渲染失败的原因。
- **不足**：对 Graphviz 自动布局缺乏预判，初稿依赖关系过密，且未充分区分调用关系与架构依赖。
- **本人修改**：确认四层边界和模块职责，精简依赖线，调整颜色和布局，并将不适合用箭头表达的触发关系改为说明文字。

## 记录 02：领域类图（2026-11-05）

- **使用场景**：依据领域层划分及实验一的数据和业务规则，绘制系统领域类图。
- **输入材料**：实验一核心数据关系、REQ-003/005/008/012/017/025，以及已确定的包图。
- **工具与环境**：同记录 01。

### 生成与迭代过程

1. 初稿包含 14 个类、3 个枚举及领域规则类，能够覆盖主要实体，但内容过多，图形被拉成长条，枚举和注释的位置不稳定。
2. 本人参考简约类图样例，要求统一英文命名，删除包框、策略类和枚举框，仅保留 11 个核心领域类。
3. 本人逐项审查业务语义，并整理书面修改意见（本地 `类图反馈意见.txt`，不入库），按优先级要求修订：
   - Customer 与 Order 由组合改为普通关联，避免账号状态影响历史订单。
   - ChangeRequest 由 0..1 改为 0..\*，同时约束同一订单最多存在一个待处理申请。
   - DailyInventory 区分 reserved 与 occupied，并将 available 改为派生属性。
   - 删除 HotelStaff 中重复的 hotelId 和 User 中不属于领域实体的认证方法。
   - 补充实际入住与退房时间、价格币种及改订处理信息，并将日志字段类型化。
4. 终稿按用户权限、预订、酒店、库存价格四个区域重新布局，并减少交叉连线。

### 人工审查与设计结论

- 用户角色采用继承表达，且一个账号仅属于一种角色。
- Order 组合 OrderNight 以保存逐晚价格快照；Customer 与 Order 使用普通关联。
- 同一房型和日期仅有一条库存记录，可售量由容量、停售量、预订量和在住量计算。
- 改订申请保留历史记录，同时限制同一订单仅有一个待处理申请。

### 优缺点分析

- **优点**：能够快速生成类、属性、方法及多重性，并依据样例统一命名和样式。
- **不足**：初稿存在过度设计，将外键、策略类和枚举全部加入类图；部分组合关系和库存字段虽形式完整，但不符合业务语义。
- **本人修改**：精简类图范围，修正关联和多重性，补充关键业务字段，并重排版面。

## 记录 03：订单状态图（2026-11-05）

- **使用场景**：绘制行为类 UML 图（选状态图），描述订单七状态及允许/禁止转换，对应 REQ-025。
- **输入材料**：实验一 REQ-010/011/014/015/017/025（状态转换条件与禁止事项）。
- **工具与环境**：同记录 01；本人指定本图使用中文标注。

### 生成与迭代过程

1. 初稿横向展示“待确认—已确认—已入住—已完成”主路径，并分别放置提前终止状态。
2. 本人要求统一使用中文标注，并核对确认不重复扣减库存、取消与未到店处置、确认超时范围等关键转换。
3. 终稿在转换线上标注触发条件和库存动作，并单独列出禁止转换。

### 人工审查与设计结论

- “已确认—已取消”包含入住日 14:00 前由顾客取消，以及次日 02:00 未到店后由工作人员联系并登记处置。
- 三十分钟确认超时仅作用于待确认订单；未到店不会自动释放库存。
- 非法转换被拒绝时，订单和库存均保持不变。

### 优缺点分析

- **优点**：在状态集合明确的情况下，能够完整生成主路径、终止状态和转换条件。
- **不足**：容易将“未到店”误解为自动超时，忽略人工联系与登记要求。
- **本人修改**：对照 REQ-014、REQ-015 和 REQ-025 修正取消及未到店转换，并补充禁止转换说明。

- `docs/design/UML/UML状态图.png`（渲染图）

## 记录 04：预订下单与酒店确认时序图（2026-11-05）

- **使用场景**：绘制交互类 UML 图（选时序图），描述预订下单主流程与酒店确认环节的对象协作。
- **输入材料**：实验一 REQ-005~011、REQ-023/025；包图模块划分；本人提供的两张时序图风格样例（PlantUML 默认风格、中文标注）。
- **工具与环境**：同记录 01，按样例使用 PlantUML 默认样式（不自定义配色）。

### 生成与迭代过程

1. 初稿包含顾客端和酒店工作台等表现层参与者，并以 alt 分支展开报价变化后的重新确认流程。
2. 本人删除仅转发请求的界面参与者，使图形聚焦角色与应用服务、领域规则之间的协作；价格或库存校验失败统一回滚并提示重新查询。
3. 终稿采用与类图一致的英文命名，删除 alt 分支，仅保留成功主线；失败回滚、幂等和确认不重复扣减库存以注释表达。

### 人工审查与设计结论

- 主线：查询（逐夜库存检查 + 逐晚报价）→ 提交（重算报价、事务占用全部夜晚）→ 酒店确认。
- 异常路径不画分支：价格变动或库存不足在事务内原子回滚（REQ-008/023），以注释说明。
- 幂等与"确认不重复扣库存"以注释标注（REQ-009/010/025）。

### 优缺点分析

- **优点**：能够完整识别查询、报价、下单、占用库存和酒店确认的交互顺序，并使用 alt 表达异常路径。
- **不足**：初稿参与者和分支过多，弱化了核心协作顺序；表现层与业务服务的职责层次不够清晰。
- **本人修改**：精简参与者和异常分支，统一英文命名，并保留原子回滚、幂等和库存约束。

## 记录 05：实验报告整理与润色（2026-11-05）

- **使用场景**：在本人确定报告结构、设计结论和图文对应关系后，使用大模型辅助组织文字并统一语言风格。
- **输入材料**：实验一需求、四张 UML 终稿、十二张界面原型、前四项 AI 使用记录及实验报告要求。

### 生成与修改过程

1. 模型按照“主要功能—软件架构与 UML—功能界面—AI 辅助过程—小结”的结构生成报告初稿。
2. 本人审查后指出，初稿存在“都写清楚”等口语化表达，部分段落复述实验要求，同一业务规则在功能、UML 和界面章节中重复出现。
3. 根据反馈，正文改为以设计目标、设计决策和设计依据为主，删除重复说明，统一“库存占用”“价格快照”“终止状态”等术语，并核对图号、界面编号和图片路径。

### 优缺点分析

- **优点**：能够快速组织多份设计材料，统一章节层级和基本措辞。
- **不足**：初稿容易沿用输入材料中的口语表达，也可能为追求完整而重复说明同一规则。
- **本人修改**：确定信息取舍，指出不规范表述，审查最终文字是否与 UML 和界面一致。

## 总结：AI 在软件设计中的适用方式

本次实验表明，大模型适合根据明确需求生成 UML 初稿、统一命名和样式，以及辅助定位 PlantUML 渲染问题；但模型不能独立判断组合关系、库存语义和状态转换等领域约束。仅进行文字和版式校对不足以保证设计正确。

较为可靠的工作流程是：首先由人工明确业务不变式和每类图的表达范围；其次由模型生成初稿；再由人工按需求编号逐项审查并形成明确的修改意见；模型据此修订和渲染；最后由人工同时检查业务语义与图形可读性。因此，AI 可以承担起草和机械修改工作，但需求解释和设计决策仍需由人完成。
